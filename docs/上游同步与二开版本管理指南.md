# Frakio Work 上游同步与二次开发版本管理指南

本文档为开发团队提供在保留自主二次开发成果的前提下，持续平滑跟踪、拉取原作者（Upstream）官方版本更新的标准化工作流与操作规程。

---

## 1. 架构拓扑：Fork 与双远程源模型

本项目采用开源界标准的 **Fork + Upstream（双远程源）** 管理模型：

```
                    ┌──────────────────────────────────────────────┐
                    │    原作者官方仓库 (MadsGao/frakio-work)       │
                    │        [Remote: upstream] (只读)             │
                    └──────────────────────┬───────────────────────┘
                                           │
                                 git fetch upstream (拉取官方更新)
                                           │
                                           ▼
┌──────────────────────────────┐   git merge upstream/main   ┌──────────────────────────────┐
│  本地工作区 (Local Workspace) │ ◄─────────────────────────  │  本地分支: upstream/main     │
│   - 已解耦的 8 大后端路由      │                             │   (对齐官方最新发布的提交)   │
│   - 已封装的前端公共组件库    │                             └──────────────────────────────┘
│   - 修复后的自定义模型通道    │
└──────────────┬───────────────┘
               │
      git push origin main (推送二开成果)
               │
               ▼
┌──────────────────────────────────────────────┐
│       个人 GitHub 仓库 (66wjz/frakio-work)    │
│           [Remote: origin] (完全读写)         │
└──────────────────────────────────────────────┘
```

### 远程源配置对照表

| 远程源名称 | 仓库地址 | 权限与职责 |
| :--- | :--- | :--- |
| **`origin`** | `https://github.com/66wjz/frakio-work.git` | **拥有完全读写权限**。存放我们团队的模块化解耦架构、自定义组件、修复补丁及新增功能。 |
| **`upstream`** | `https://github.com/MadsGao/frakio-work.git` | **只读源**。仅用于在作者发布新版本（如 v1.5.0+）时拉取官方代码，不向其直接推送。 |

## 2. 日常二次开发工作流

在进行任何新功能开发或页面改造时，请遵循以下规范：

### 2.1 本地开发与提交
```bash
# 1. 确认当前处于 main 分支
git checkout main

# 2. 查看当前修改状态
git status

# 3. 暂存并提交代码
git add .
git commit -m "feat(module): 新增业务功能描述"

# 4. 推送到个人 GitHub 仓库备份
git push origin main
```

## 3. 当原作者发布新版本时：标准同步规程（3 步法）

当原作者在 GitHub 发布了新版本更新时，请在项目根目录下按以下步骤同步：

### 步骤 1：抓取原作者最新提交
```bash
# 抓取原作者的所有新分支与 Tag（不会修改当前工作区的任何代码）
git fetch upstream
```

### 步骤 2：合并官方更新到本地工作区
```bash
# 将原作者的最新主分支合并进我们当前分支
git merge upstream/main
```

#### 合并处理机制：
1. **自动合并（Fast-Forward / Clean Merge）**：
   - 对于原作者新增的工具、Python 脚本或我们未曾改动的底层文件，Git 会**100% 全自动平滑合入**。
2. **三方冲突消解（Conflict Resolution）**：
   - 如果原作者在 `server.mjs` 或 `main.tsx` 中修改了我们已经解耦提取的旧逻辑，VS Code 会在左侧「源代码管理」高亮标出冲突文件。
   - **冲突消解原则**：
     - **新功能/新 API**：按照我们的规范，将作者新增的 Express 路由迁移到对应的 `apps/api/routes/*.mjs` 子模块中，或将新 UI 封装入 `apps/web/src/components/*`。
     - **保留我们的解耦结构**：优先保留我们精简后的主入口与通用组件调用。

### 步骤 3：验证并推送到个人仓库
```bash
# 1. 运行语法检查与类型检查
npm run check:syntax
npm run typecheck

# 2. 验证通过后推送到个人仓库
git push origin main
```

## 4. 多运行时（Hermes / Pi / Codex / Claude Code）环境隔离说明

在 Frakio Work 中创建与使用多 Agent 时，底层环境具备**完全的沙箱隔离性**，绝不会影响或污染开发者本地原有的 CLI 或全局环境：

### 各运行时隔离策略

| 运行时类型 | 隔离机制与存储路径 | 对本地全局环境的影响 |
| :--- | :--- | :--- |
| **Hermes Agent** | 每个 Agent 独立分配 Profile 目录：`~/.hermes/profiles/<profile-name>/`。拥有独立的 `config.yaml`、独立的会话 SQLite 数据库 `session_db`、独立的技能与长期记忆 `memory.md`。 | **完全隔离**。即使本地安装了 `hermes-agent`，运行也完全限定在对应的 Profile 子空间内。 |
| **Pi Runtime** | 独立技能沙箱：`~/.frakio-work/runtimes/pi/agents/<agentId>/skills`。通过专属进程池调度。 | **完全隔离**。不干扰系统全局配置。 |
| **Codex Runtime** | 独立沙箱根路径：`~/.frakio-work/runtime/homes/codex`，独立 Skill 路径：`~/.frakio-work/runtimes/codex/agents/<agentId>/skills`。 | **完全隔离**。重定向了用户 Home 路径与执行 Realm。 |
| **Claude Code** | 独立沙箱根路径：`~/.frakio-work/runtime/homes/claude`，独立 Skill 路径：`~/.frakio-work/runtimes/claude/agents/<agentId>/skills`。 | **完全隔离**。通过 Frakio 专属的 `ClaudeAgentSdkBridge` 进行调度与生命周期管理。 |

> **核心结论**：Frakio Work 中所有 Agent 的新增、删除、配置修改与记忆更新，均在专属数据目录（`~/.frakio-work/` 与 `~/.hermes/profiles/`）中闭环进行，**不会覆盖、不会破坏、也不会串扰**您本地电脑原本配置的任何 Agent 环境。
